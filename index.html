01 In build · MVP demo-ready Kale Logistics · 2025–26

Trade Compliance Engine

A shipment has to satisfy about a dozen regulatory bodies before it crosses a border. Today that check is done by hand or skipped — so problems surface once the cargo is already stopped. This runs the whole check before anything reaches an authority.

What I did

  • Defined the product from the problem up — scoped which compliance checks exist, who owns each failure, and which ones an authority will actually reject a filing over.
  • Designed the 21-agent architecture across 5 disciplines: party screening, cargo & controls, classification, filing/cost/duty, and sustainability.
  • Specified the verdict model — clear / review / match — and the evidence each verdict has to carry so a broker can defend it to an auditor later.
  • Ran the market and competitive study, sized the opportunity bottom-up from declaration volume, and drove the requirement sessions with customs brokers and forwarders.
  • Drove delivery with engineering — OCR + LLM extraction, parallel orchestration, run history and audit, and the consolidated compliance report.

The call I'd defend hardest: 21 agents, not one model

The instinct is one large prompt over the whole document set. I argued for decomposition on product grounds — a wrong HS code and a missed sanctions match are different incidents with different owners, so collapsing them into one output makes neither fixable. Sanctions lists change daily and tariff schedules annually, so a monolith forces the slowest component to set everyone's refresh cadence. And you can only set an accuracy target for a check you can isolate.

The same logic produced the three-state verdict. In screening, a false negative is a regulatory incident with unbounded cost; a false positive costs an analyst two minutes. So tune hard toward recall and spend the budget making review cheap — which needs a “review” state that a pass/fail system doesn't have.

02 Live · 20 ports Kale Logistics · 2024–26

Maritime Single Window

A vessel call touches about a dozen agencies — customs, port authority, immigration, health, marine, the terminal — each with its own form and deadline. Agents used to re-key the same facts into every one. Now they enter the call once and every agency format is derived from it.

What I did

  • Owned the 0→1 build — defined the problem space, scoped the roadmap, and drove engineering delivery from first principles to a live product.
  • Designed the canonical vessel-call model that every agency's format is derived from, instead of building a separate integration per agency.
  • Ran requirement sessions with agencies and shipping agents to establish each authority's mandatory field set and where the same real-world fact was named three different ways.
  • Anchored the rollout on Port Klang — deliberately the hardest corridor — so the model was proven against the most complex agency mix before scaling across Southeast Asia.
  • Built the rollout motion so onboarding a new port is a configuration exercise rather than a rebuild.

What it's achieved so far

The call I'd defend: build the model before the integrations

The tempting path is agency-by-agency integrations — each one demos beautifully. But it produces N bespoke pipelines and no reusable asset, and every new port becomes a rebuild wearing a different name. I built the canonical model against one agency first, proved derivation worked, and only then let integrations become a repeatable motion.

What I got wrong: I underweighted change management. The system was correct well before the agents trusted it — and a correct output a user won't sign is worth nothing. The fix was mundane: a side-by-side view of the hand-filled form against the generated one, so an agent could verify at a glance instead of redoing the work to check our answer. It should have shipped in the first release. I now treat “how does this user verify the output without redoing it?” as part of the definition of done.

03 Live in production Kale Logistics · 2025

AI Document Generation

Port operations teams were hand-drafting the same twenty document types from the same scattered source files, thirty minutes at a time. This reads the sources and drafts the document — with every field traceable back to where it came from.

What I did

  • Scoped and launched the feature end to end — RAG pipeline over source documents plus LLM generation against each authority's mandated format.
  • Chose the document types by volume × manual effort, not by what was easiest to build, so the first release removed the largest real block of work.
  • Designed the extraction → generation → review flow, including per-field confidence and source attribution, so an operator can verify a draft without re-reading six PDFs.
  • Set the measurement approach — baseline timed per document type, weighted by the actual daily mix rather than the slowest type.

How I work

Four things I've come to believe

Each one paid for by a decision that went well, or badly.

01

Automate the step people skip, not the step people hate.

The slow step is visible and everyone's already optimising it. The valuable one is quietly skipped because doing it properly is too painful — in trade, that's the pre-filing compliance check. Nobody runs it; everybody pays for it at the border. That gap between where pain is felt and where it was caused is usually where the product is.

02

Decide what “wrong” costs before you decide what “good” looks like.

A model at 95% is excellent for drafting a document and unacceptable for screening a sanctioned party. Same accuracy, opposite verdict, because the cost of the missing 5% differs by orders of magnitude. I set the failure cost first and let the accuracy bar and the review design fall out of it.

03

A number without a denominator is a story.

“93% faster” means nothing until you say across which document types, at what volume, against whose baseline, and what it excludes. I'd rather present a smaller number I can defend in a room full of sceptics than a bigger one that collapses on the second question.

04

Regulated users don't want autonomy. They want defensibility.

A customs broker isn't asking the system to decide for them. They want something they can put in front of an auditor eighteen months later and explain — which list, which version, which match, who signed. Here the audit trail isn't bolted on at the end; it's the product.
