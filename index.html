01 In build · MVP demo-ready Kale Logistics · 2025–26

Trade Compliance Engine

A shipment has to satisfy about a dozen regulatory bodies before it crosses a border. Today that check is done by hand or skipped — so problems surface once the cargo is already stopped. This runs the whole check before anything reaches an authority.

What I did

  • Defined the product from the problem up — scoped which compliance checks exist, who owns each failure, and which ones an authority will actually reject a filing over.
  • Designed the 21-agent architecture across 5 disciplines: party screening, cargo & controls, classification, filing/cost/duty, and sustainability.
  • Specified the verdict model — clear / review / match — and the evidence each verdict has to carry so a broker can defend it to an auditor later.
  • Ran the market and competitive study, sized the opportunity bottom-up from declaration volume, and drove the requirement sessions with customs brokers and forwarders.
  • Drove delivery with engineering — OCR + LLM extraction, parallel orchestration, run history and audit, and the consolidated compliance report.

The call I'd defend hardest: 21 agents, not one model

The instinct is one large prompt over the whole document set. I argued for decomposition on product grounds — a wrong HS code and a missed sanctions match are different incidents with different owners, so collapsing them into one output makes neither fixable. Sanctions lists change daily and tariff schedules annually, so a monolith forces the slowest component to set everyone's refresh cadence. And you can only set an accuracy target for a check you can isolate.

The same logic produced the three-state verdict. In screening, a false negative is a regulatory incident with unbounded cost; a false positive costs an analyst two minutes. So tune hard toward recall and spend the budget making review cheap — which needs a “review” state that a pass/fail system doesn't have.

02 Live · 20 ports Kale Logistics · 2024–26

Maritime Single Window

A vessel call touches about a dozen agencies — customs, port authority, immigration, health, marine, the terminal — each with its own form and deadline. Agents used to re-key the same facts into every one. Now they enter the call once and every agency format is derived from it.

What I did

  • Owned the 0→1 build — defined the problem space, scoped the roadmap, and drove engineering delivery from first principles to a live product.
  • Designed the canonical vessel-call model that every agency's format is derived from, instead of building a separate integration per agency.
  • Ran requirement sessions with agencies and shipping agents to establish each authority's mandatory field set and where the same real-world fact was named three different ways.
  • Anchored the rollout on Port Klang — deliberately the hardest corridor — so the model was proven against the most complex agency mix before scaling across Southeast Asia.
  • Built the rollout motion so onboarding a new port is a configuration exercise rather than a rebuild.

The call I'd defend: build the model before the integrations

The tempting path is agency-by-agency integrations — each one demos beautifully. But it produces N bespoke pipelines and no reusable asset, and every new port becomes a rebuild wearing a different name. I built the canonical model against one agency first, proved derivation worked, and only then let integrations become a repeatable motion.

What I got wrong: I underweighted change management. The system was correct well before the agents trusted it — and a correct output a user won't sign is worth nothing. The fix was mundane: a side-by-side view of the hand-filled form against the generated one, so an agent could verify at a glance instead of redoing the work to check our answer. It should have shipped in the first release. I now treat “how does this user verify the output without redoing it?” as part of the definition of done.

Port operations teams were hand-drafting the same twenty document types from the same scattered source files, thirty minutes at a time. This reads the sources and drafts the document — with every field traceable back to where it came from.

How I work

What I believe, how I think, what I use

Four convictions, one worked example of the reasoning behind them, and the tools underneath.

01

Automate the step people skip, not the step people hate.

The slow step is visible and everyone's already optimising it. The valuable one is quietly skipped because doing it properly is too painful — in trade, that's the pre-filing compliance check. Nobody runs it; everybody pays for it at the border. That gap between where pain is felt and where it was caused is usually where the product is.

02

Decide what “wrong” costs before you decide what “good” looks like.

A model at 95% is excellent for drafting a document and unacceptable for screening a sanctioned party. Same accuracy, opposite verdict, because the cost of the missing 5% differs by orders of magnitude. I set the failure cost first and let the accuracy bar and the review design fall out of it.

03

A number without a denominator is a story.

“93% faster” means nothing until you say across which document types, at what volume, against whose baseline, and what it excludes. I'd rather present a smaller number I can defend in a room full of sceptics than a bigger one that collapses on the second question.

04

Regulated users don't want autonomy. They want defensibility.

A customs broker isn't asking the system to decide for them. They want something they can put in front of an auditor eighteen months later and explain — which list, which version, which match, who signed. Here the audit trail isn't bolted on at the end; it's the product.

Principles are easy to claim and hard to evidence. So here is one decision worked end to end — the reasoning, the constraints, and the options I threw away. Step through it.

The problem on the table

A customs broker has 200 shipments to clear before the filing window closes. Twenty-one agents have just returned a verdict on every one of them. What does she see first?

Step 01 · Observe

Watch the job. Don't ask about the screen.

I sat through a filing window and asked nothing for the first hour. The question I wanted answered wasn't "what do you want" — it was "what do you already do when the tool isn't helping".

What I saw

Nobody read the results top to bottom. Each broker scanned for the two or three shipments they already suspected — a new consignee, an unfamiliar port pair — cleared them, and moved on. The system's ordering was decoration. They had their own, carried in their head, and it was better than ours.

What I rejected

Running a survey first. Ask a broker what they need and you get "a dashboard" — everyone says a dashboard. The useful signal was the workaround, not the wish list.

If users have built a private ranking to survive your product, that ranking is your spec. Go and find it before you design anything.

Step 02 · Frame

This was never an accuracy problem.

The agents were right. That was the uncomfortable part — the screen was full of correct information that nobody had the minutes to read.

The question I'd been asked

"How do we display twenty-one agent verdicts per shipment without overwhelming the user?" A layout question. It has layout answers, and all of them are wrong.

The question I reframed it to

"Which of today's 200 shipments deserves a human minute, and which minute gets spent where?" Attention is the scarce resource being allocated. Everything downstream follows from saying that out loud.

What I rejected

Tuning the model further. Another two points of precision would not have bought a single extra minute of attention. Right answer, wrong bottleneck.

Step 03 · Constrain

Write down what can't move, before you get attached to an idea.

In a regulated product the constraints aren't obstacles to the design. They're most of it. I list them before sketching, because otherwise I fall in love with something illegal.

Regulatory — fixed

Every verdict stays retrievable with the list it hit, that list's version, and the timestamp — whether or not a human ever looked at it. I can defer a result. I can never drop one.

Organisational — fixed for now

Brokers are measured on shipments cleared, not checks read. Any design asking them to read more, for its own sake, loses to the incentive and should.

What I rejected

An auto-clear that quietly discards low-risk results to shorten the queue. It tests beautifully and it is indefensible eighteen months later in front of an auditor asking what the system decided not to show.

Step 04 · Trade off

The call I'd defend: sort by consequence, not confidence.

Confidence is what the model knows about itself. Consequence is what it costs us to be wrong. Those rank the queue very differently, and only one of them is about the user's actual risk.

The decision

A 72%-confidence near-match on a sanctions list outranks a 61%-confidence flag on a routine HS code — because one is a licence-losing event and the other is a correction. Same shaped uncertainty, incomparable stakes.

What it costs me

The queue sometimes leads with something the broker finds obvious, and that's mildly irritating. I took that trade knowingly: an unnecessary summons is cheap and a missed match is not.

What I rejected

Blending everything into one 0–100 risk score. It ranks well and it cannot be explained to an auditor — which fails the only test that matters here.

Step 05 · Design

Only now does it become a screen.

Five steps in. By this point the interface is close to a formality — the hard decisions are already made, and the layout is just where they become visible.

Queue ordering, in plain terms

for each shipment:
  rank = consequence_if_missed  // licence > penalty > correction
       × verdict_state          // match > review > clear
       × recency_of_list_change

never: hide a clear   → collapse it, keep it retrievable
always: carry list + version + matched field + signer

Three states, not a percentage

Clear · Review · Match. A broker can act on a state. Nobody has ever made a different decision at 84% than at 86%, and the number invites an argument that the ladder settles.

Every row opens into its evidence

Which list, which version, which field matched, who signed it off. The audit trail isn't a report generated later — it's the same object the broker is already reading.

Step 06 · Measure

Name the number that would prove me wrong.

I try to pick the disconfirming metric at design time, while I still have nothing invested in the answer. After launch I'll be motivated to choose kindly.

The number I actually watch

How often a broker moves a Review straight to Clear without opening the detail. That's the tell that my ranking is crying wolf — they've learned the top of the queue isn't worth reading, and I've rebuilt the problem I set out to fix.

The number that decides whether it worked

Matches caught before filing versus matches surfaced downstream by a customs query. Time saved is a nice headline; escaped matches are the thing the product exists to stop.

What I rejected

Satisfaction scores. A queue that never interrupts anyone scores wonderfully right up to the audit.

Pair this with principle 03 — a number without a denominator is a story. Both of these have one: per broker, per filing day, against the pre-launch baseline.
